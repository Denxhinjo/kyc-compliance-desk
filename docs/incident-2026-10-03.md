# Incident: five days of silently failing decisions

**3–8 October 2026.** Every automatic decision on the production system failed
for five days. Nothing was corrupted and no applicant was decided wrongly, but
nothing was decided at all — and every monitoring signal stayed green
throughout.

This is a demo with invented applicants, so the cost was nil. The mechanism is
not a demo problem, and that is why it is written up.

---

## What happened

The system is two deployed pieces sharing one database: a **web app** for
applicants and compliance officers, and a **worker** that does the scoring in
the background. The database's structure is changed by numbered files called
*migrations*, applied deliberately.

A change was in progress that added a column to the `decisions` table — the
version of the scoring rules each decision was taken under. The worker code was
updated to write that column. The migration that *creates* it had not yet been
applied to production.

Normally that gap does not exist, because the code and the migration are
deployed together, in a planned order. Here the worker deployed **by itself**:
its hosting project was connected to the source repository and redeployed on
every push. So from the first push after the code change, on 3 October, the
live worker was writing to a column the live database did not have.

Every automatic decision therefore failed with *"column does not exist"*.

## How long, and how much

**Five days**, 3 to 8 October. In that window the worker recorded **zero**
automatic decisions.

The practical damage was limited by something unrelated: the applications that
would have been decided were already stalled waiting on the identity vendor, so
very little work reached the failing step. Had the system been busy, the queue
would have filled with failed jobs instead.

## Why nothing was corrupted

Each job runs inside **one database transaction** — an all-or-nothing unit. The
worker scores the applicant, writes the score, and records the decision; if any
part fails, the whole thing is undone as though it never ran.

So each failure rolled back cleanly. No half-written decisions, no applications
left with a score but no verdict, no partial state for anyone to untangle. The
jobs stayed in the queue, marked failed, waiting.

This is worth stating precisely because it is the difference between an
embarrassment and a crisis. The system did not do the wrong thing; it did
nothing, repeatedly, and kept the evidence.

## Why it went unnoticed

The worker is called every few hours by a scheduled job, which makes an HTTP
request to an endpoint that processes a batch of work.

**That endpoint returned "success" whether or not the work succeeded.** Each
job's failure was caught, recorded on the job's own row and written to a log —
and then the endpoint reported that the request had completed, which was true
and useless. The scheduled run went green every time.

So the only signal anyone looked at was reporting on the wrong thing: whether
the request arrived, not whether the work happened.

This is a pattern the project had already named — *something that looks like a
check and is not one* — and had already found twice elsewhere. It was not
recognised here, in the live system, where it mattered most.

## How it was found

Not by monitoring. By preparing the rollout.

Before applying the migrations to production, the plan was rehearsed against a
copy of the live database, and the preparation included a question that had not
been asked before: *has the code deploy already happened on its own?*

Checking the hosting provider's deployment records answered it — one production
deployment per push since 3 October, all of the worker project. Comparing the
live site against a known marker showed the web app, by contrast, had not been
rebuilt since September. The asymmetry was the whole story: **one half of the
system had been deploying itself for five days, and the other had not.**

The rehearsal also found that the rollout could not have been performed as
written — the migration runner applied files in numeric order, and the required
order was different. Both problems were found by trying to do the thing rather
than by reading about it.

## What prevents it now

**The worker no longer deploys itself.** The repository connection has been
removed. Worker deployments are now deliberate and manual, which means code and
migrations can be ordered with respect to each other — the property whose
absence caused this.

**The endpoint now reports failure.** If any job in a batch fails, it returns an
error status instead of success, and the scheduled run goes red. Proven both
ways before shipping: a forced failure turns the call red, a clean queue leaves
it green. The counts of failed and parked jobs are in the response, so a reader
can tell a transient blip from work the system has given up on.

**Re-proven on production, 9 October**, after the credential rotation: a job
with an unregistered type was put on the live queue, the scheduled run was
triggered by hand, and it went red with the endpoint returning 500. Removing
the job and re-running returned it to green. The job parked on its first
attempt without retrying and touched no application, which is why it was the
mechanism chosen.

That proof found one more thing, and it is the same defect in miniature. The
run went red correctly, but **the response body never reached the log.** The
workflow runs under `set -e`, so the step died on the line that captured
curl's output and the line that printed it never ran. The log said
`curl: (22) ... error: 500` and stopped — the `failed` and `parked` counts
described in the paragraph above were sent by the endpoint and then discarded
by the thing receiving them. Fixed by capturing curl's exit status instead of
letting the shell abort, printing the body, and then failing. A reader now sees
the counts on exactly the runs where they matter.

Worth stating plainly: this was found by forcing a failure, not by reading the
workflow, and it had survived being written, reviewed and shipped as the fix
for an incident *about* unreadable signals.

**The ordering is written down and rehearsed.** The rollout sequence, what each
step does, and what breaks if it is done out of order are documented, and the
whole sequence was executed against a copy of production before being run on it.

## What this does not prevent

A deliberate deploy can still go out ahead of its migration — a human can do in
one command what the automation was doing on a schedule. The protection is now
procedural rather than structural: the order is documented, and the endpoint
will say so within hours rather than never.

Nor does it guarantee anyone *reads* the red. A failing scheduled run is only
useful if it is noticed, and this incident is the evidence that a green signal
nobody questions is worth less than no signal at all.

---

## For a reader deciding whether this matters

The honest summary: a background service deployed itself ahead of a database
change, every unit of work it attempted failed, each failure rolled back
cleanly, and the health check reported success for five days because it was
measuring the wrong thing.

The three lessons are not specific to this system.

1. **Two things that must change together must deploy together.** Automatic
   deployment on one half of a system and manual on the other is not two
   policies, it is one accident waiting for a schedule.
2. **A health check that cannot fail is not a health check.** Ask what it would
   take to make it red. If nothing inside the system can, it is reporting on
   the network and not on the work.
3. **Rehearse the rollout against a copy.** Two problems here were found by
   attempting the procedure, and neither would have been found by review.
